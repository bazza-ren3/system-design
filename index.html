01
Context & Design Goals

One cluster, many customers

This platform runs a document-intelligence app — document ingestion, RAG search, and LLM-driven workflows — for several customers on shared EKS infrastructure, isolated per tenant rather than per cluster.

Tenant isolation

Each customer gets its own namespace, tainted node pool, RDS cluster, EFS filesystem and S3 bucket — compute and data never cross tenant lines.

No static credentials

GitHub deploys assume AWS roles via OIDC. In-cluster secrets come from HashiCorp Vault, not baked into images or values files.

Elastic, spot-first compute

Every node group runs on SPOT capacity behind the cluster-autoscaler, scaling 1→6 nodes per tenant on demand.

Mesh-managed ingress

Istio terminates HTTP behind an NLB that does the actual TLS work (ACM), with one Gateway + VirtualService per tenant for path-based routing.

Centralized model access

LLM calls go through a shared litellm gateway backed by Bedrock, rather than every tenant service holding its own model credentials.

Gated production changes

UAT deploys auto-apply; production deploys require reviewer approval via GitHub Environments before helmfile sync runs.

One managed node group per tenant

A shared default pool runs cluster-wide system/shared components; each tenant gets its own tainted, autoscaled node group so noisy neighbors can't compete for CPU.

06
Secrets & Identity

Vault in the cluster, OIDC at the edge

Two separate trust paths: workloads authenticate to Vault with their Kubernetes service account; GitHub Actions authenticates to AWS with a short-lived OIDC token. Neither stores a long-lived credential.

Vault (HA)

vault-0/1/2 — Raft consensus, KMS auto-unseal

Agent injector

Mutating webhook adds a vault-agent sidecar to annotated pods — visible as the 2/2 containers on server/ingestor/workflow

Secrets operator

Syncs VaultStaticSecret CRDs into native Secret objects for workloads that read env vars directly (e.g. watcher)
Deploy-time identity
GitHub Actions exchanges its OIDC token for a short-lived AWS role via aws-actions/configure-aws-credentials — no AWS_ACCESS_KEY_ID stored anywhere in the repo or secrets.

LLM Gateway

One gateway, one place to meter and rate-limit

Tenant services don't call model providers directly — everything routes through a shared litellm deployment, which is the only thing holding Bedrock IAM permissions in practice.

Bedrock IAM permissions are attached to every tenant node group's role, but the intended call path is through litellm — direct pod-to-Bedrock calls are possible, not the designed path.

Plan and apply deliberately don't share a saved plan file: the kubernetes provider's aws_eks_cluster_auth token is short-lived (~15 min), and a review pause between a saved plan and its apply could let that token expire mid-apply.
